# Codex 中心化多 CLI 协作

> 状态：`current`
>
> 采用日期：`2026-07-24`
>
> 采用方式：用户明确决定直接作为正式元开发规则；后续以实际问题驱动修订

本文件是本仓库多 CLI 开发协作的唯一详细规则。`AGENTS.md`只保存摘要和路由。这里的
“多 CLI”只描述 Agent 如何开发本产品，不改变产品本身“不提供开放式多 Agent”的公开边界。

## 目标与非目标

目标：

- 用户只从 Codex 进入开发，不需要分别维护多个 Agent 对话；
- 没有开发任务时，Codex 作为项目规划者陪同用户讨论现状、方向、优先级和后续提示词；
- 在真正执行前让用户看见当前可用 CLI、模型和额度，再自行选择开发 Worker；
- 用不同 CLI 的能力差异并行推进独立工作，并降低单一订阅额度的消耗速度；
- 通过自然派发、单一写入者、Git 检查点和交接回执保持可恢复性。

当前不做：

- 不开发自动调度程序、自动模型评分或自动额度分配；
- 不让 Codex 自动替用户选择开发 CLI；
- 不因为安装了 CLI 就默认授予模型调用、费用、凭据、网络或外部写入权限；
- 不把多个 Agent 放进同一 worktree 同时写入；
- 不把 Worker 当作按预设步骤运行的机械执行器；
- 不为这套流程新增 `PLANS.md`、个人 Skill 或第二套任务文档。

## 角色

- **用户**：与 Codex 动态决定产品方向、不可逆取舍、风险与费用边界，并选择开发 CLI；
- **Codex**：唯一用户入口和默认项目规划者，负责上下文恢复、方向讨论、CLI 状态、自然
  派发、写入权、worktree、消息转述和工程集成；除非用户明确选择 Codex 实现，否则不作为
  开发 Worker；
- **Worker**：用户选中的 code CLI，在一个有边界的工作会话中自主调查、制定技术计划、
  维护过程文档、完成实现和其能力范围内的专业自验；
- **专业验收者**：由最适合该证据形态的 Worker 承担，例如动态网页和视频由具备对应视觉
  能力的 CLI 检查；
- **用户验收**：用户可见体验、产品取舍和最终主观质量始终由用户实际使用后确认。

Codex 不是所有专业结果的默认最终验收者。它只对自己能够可靠检查的工程合同形成结论。

## 标准流程

```text
Codex 与用户持续讨论项目现状和开发方向
→ 必要时进入 Plan 模式
→ 双方自然形成下一项开发决定
→ Codex 生成 CLI 状态卡
→ 用户选择开发 Worker
→ Codex 创建 worktree 并发送协作式委托
→ Codex 向用户逐字公开实际发送内容
→ Worker 自己写入过程文档并在有边界的多轮会话中实现
→ Codex 向用户摘要转述 Worker 的每次回复
→ Worker 形成 Git 检查点和交接回执
→ Codex 做工程集成，专业 Worker 做专项验证
→ 用户实际体验验收
```

只讨论、解释、只读调查或尚未决定下一项开发工作时，不生成 CLI 状态卡，也不启动 Worker。

## 规划讨论与任务形成

没有开发任务时，Codex 读取当前产品事实、活动状态和路线，与用户讨论“接下来什么最值得
做、为什么、暂时不做什么”。讨论可以持续多轮并动态改变方向，不要求生成任务卡、固定
模板或仓库文档。

当用户和 Codex 已经自然形成一个可以交给 CLI 执行的开发决定，并且用户明确要求开始或
派发时，Codex 用普通语言复述双方决定。用户没有异议即可进入 CLI 状态与选择阶段，不再
额外要求一次表格化确认。

划分规则：

- 两个结果可以分别验收时，拆成两个任务；
- 相邻问题不阻塞当前结果时，进入未来 Issue，不静默扩大范围；
- 常规库、文件、类和测试形态由执行 Agent 决定，不升级给用户；
- 产品结果、公开主张、费用、隐私、外部状态或不可逆取舍变化时，必须重新确认范围；
- 同一结果内的技术方向调整可以继续当前 Worker 会话；若变成另一项产品结果或风险边界，
  先让 Worker 留下检查点，再回到 Codex 与用户的规划讨论。

## Plan 模式与持久化文档

Plan 模式是收敛方法，不是第二套事实系统。它适用于复杂、模糊、跨模块、有明显产品取舍或
技术未知的任务，用来调查上下文、追问、比较方案和形成范围。范围与方案明确的小修复、
机械修改、状态查询和单纯问答不必进入 Plan 模式。

Plan 模式中的对话和计划默认是草稿。Codex 不在派发前替 Worker 写过程文档；Worker 启动
后读取双方决定和仓库事实，自行生产并消费执行文档：

| 载体 | 唯一职责 |
| --- | --- |
| 普通讨论 / Plan 模式 | 探索、追问和收敛，不作为仓库权威事实 |
| `spec.md` | Worker 写入对开发决定的理解、边界和可观察结果 |
| `plan.md` | Worker 自主制定并持续更新执行顺序、检查点、验证与恢复 |
| Codex 当前计划清单 | 当前会话的临时进度，不单独持久化 |
| `result.md` | Worker 记录实际结果、证据、限制与剩余问题 |
| `review.md` | 独立复核者记录 finding；实现 Worker 不能给自己出具独立复核 |
| `docs/status.md` | 当前写入者更新活动工作和检查点；交接后由 Codex 更新集成状态 |
| GitHub Issue / PR | 未来任务、候选 diff、Checks 与外部回执 |

不要把 Plan 模式全文复制进仓库，也不要同时维护 `PLANS.md` 和活动 `plan.md`。

## CLI 状态卡

### 生成时机

用户和 Codex 决定下一项开发工作后、派发 Worker 前生成。讨论结束后若间隔较长、切换
Worker、开始新的独立任务、进入并行任务或 CLI 报告额度 / 登录异常，必须刷新。

### 内容

```text
执行前 CLI 状态卡
核实时间：

Codex：安装 / 认证 / 模型 / 额度可见性 / 当前任务 / 写入可用性
Kimi：安装 / 认证 / 模型 / 5h 额度 / 周额度 / Extra Usage / 写入可用性
Qoder：安装 / 认证 / 模型 / 额度可见性 / 写入可用性

当前仓库 / 分支 / worktree：
当前写入者：
等待用户选择：
```

每个字段使用 `已确认`、`用户授权`、`待确认` 或 `不可用`，并写明核实时间。不能读取的额度
保持 `待确认`，不能凭套餐名称或历史值推断。

Kimi Code 的当前额度优先通过其 `/usage` / `/status` 能力或本机对应只读接口核实；具体
数值是易变运行事实，不写入长期文档。其他 CLI 只有在实际接入后才报告为可用。

Codex 只报告事实，不给出自动选择结果。用户的 CLI 选择只对本次已讨论的开发工作有效。

## 外部授权与额度

Git 跟踪的规则永远不能授予 Provider、费用、凭据、网络、部署或外部写入权限。用户选择
某个 CLI，只表示允许它在当前讨论结果、数据边界、工作树和停止条件内工作；任何范围外风险
仍需单独授权。

任务启动前固定可获得的短窗 / 长窗额度、费用边界和停止条件。运行中发生以下情况时停止并
回到 Codex：

- 额度不足或无法核实；
- CLI 登录、模型或能力与状态卡不一致；
- 调用产生未声明费用或需要范围外网络 / 外部写入；
- Worker 进入无界重试、重复循环或不能形成检查点。

## Worker 会话

默认采用“一个任务一个有边界的多轮会话”：

- 同一会话完成阅读、实现、测试、观察结果和有限修正；
- 复杂前端、动态视觉、跨模块功能和需要连续上下文的工作不拆成连续单轮调用；
- 命令查询、错误解释、简单只读审查和范围明确的机械小修改可以单轮完成；
- 独立复核使用新的只读会话，避免实现上下文影响判断；
- 任务范围改变、上下文明显污染、额度触线或切换 CLI 时结束原会话。

长期连续性不能依赖 Worker 聊天记录，必须依赖仓库文件、Git 状态、测试和交接回执。

## 协作式派发、身份与写入隔离

Codex 把与用户形成的决定转成一条接近人类开发者委托的自然消息。消息应说明产品背景、
为什么现在做、用户希望得到什么、已有参考和真正不可突破的风险边界，并明确邀请 Worker：

- 先阅读仓库和当前状态，自主判断实现路径；
- 自己编写和维护 `spec.md`、`plan.md`、`result.md` 及执行期状态；
- 自己选择常规文件、库、实现顺序和验证方法；
- 可以质疑前提、提出更好方案并报告意外发现；
- 只有改变产品方向、外部风险、费用、隐私或不可逆边界时才停止并返回讨论。

除非某个文件、接口、测试或命令本身就是已确认的公共合同，Codex 不在消息中规定逐文件、
逐类或逐命令的机械步骤。安全与授权边界必须明确，但不能借详细派发清单代替 Worker 的
技术判断。

`AGENTS.md` 是多个 CLI 共享的项目规则，不为 Kimi、Qoder 或 Codex 固定永久身份。当前
身份由派发消息说明：

- Codex 默认是项目规划者和调度者；
- 被选择的 CLI 是本次开发 Worker；
- 被独立调用进行复核的 CLI 是只读复核者。

如果派发消息没有说明角色，CLI 在写入前必须询问。仓库已有权威 `AGENTS.md`，任何 CLI
都不得用 `/init` 或类似初始化命令直接覆盖；需要生成建议时先写入 Git 外临时位置比较。
当前不为不同 CLI 建立重复的项目级身份文件。

一个 worktree 同一时间只有一个写入者。需要并行写入时必须使用独立分支和独立 worktree。
Worker 负责生产和消费本任务的过程文档，Codex 不在派发前代写。Worker 写入期间，Codex
只能做只读协调，或在不重叠的独立 worktree 中推进另一项已经明确
授权的任务；不能在 Worker 完成前修改其工作树。

Worker 停止写入并提交候选后，Codex 才能进行集成。Codex 可以记录集成状态，但不能重写
Worker 的执行证据。集成若改变专业结果，原专项回执失效，
必须重新交给适合的 Worker 检查。

## 双向消息透明

Codex 每次向 CLI 发送初始委托、追问、纠偏或补充消息后，立即告诉用户：

- 发送给哪个 CLI、会话和 worktree；
- 附带了哪些文件、网页、图片或视频；
- 实际发送的完整消息原文。

Codex 不能只展示美化后的摘要，也不能在后台静默改变方向。运行器参数、权限和外部边界若
会影响 Worker 行为，也必须一并说明。

CLI 每返回一条模型回复或阶段性结论，Codex 都向用户提供一次关键信息摘要，至少提取：

- Worker 对当前工作的理解；
- 已完成内容与作出的技术决定；
- 意外发现、风险、阻碍和需要用户决定的问题；
- 验证状态与下一步。

摘要必须区分 `Worker 报告`、`Codex 已核验` 和 `待核验`，不能把 Worker 的口头结论直接
写成事实。无需逐字转发回复或内部工具日志；涉及范围、费用、权限、失败或用户决定时，
保留必要的精确原句。用户随时可以要求查看某条完整回复。

## 交接回执

每个 Worker 会话结束时必须留下可恢复的交接结果。格式由 Worker 决定，但至少覆盖已完成
和未完成内容、实际修改、验证、专业自验、阻碍与风险、额度 / 耗时、Git 状态 / commit、
恢复方式和唯一下一步。

Codex 先核对真实 diff、Git 状态和测试，再使用回执。口头总结不能覆盖仓库事实。

## 分层验收

- **Worker 专业自验**：证明其负责的视觉、视频、特定框架或其他专项结果；
- **Codex 工程集成**：证明范围、依赖方向、测试、响应式、可访问性、性能、状态和文档一致；
- **正式独立复核**：只在仓库复核规则要求时对固定候选执行；
- **用户验收**：证明用户可见结果达到目标。

四者不能互相冒充。专业 Worker 通过不代表工程集成完成，自动化通过不代表视觉通过，用户
喜欢页面也不代表生产、安全或费用门已经满足。

## 文档保留

元开发规则以本文件、`docs/meta/README.md`、`principles.md` 和必要工程文档为当前事实。
避免为每次讨论、实验、Worker 会话或规则修订新增永久文档：

- 原始聊天、CLI stdout、模型原文和临时计划不进入 Git；
- 元开发工作完成后，把长期规则写入权威文件，把一次关键经验按需压缩为案例或演化日志，
  随即删除活动 / 完成工作包；同一变化不同时保留规则、实验、四文件任务和长案例；
- 普通产品完成工作只保留规范化 `result.md`，强制独立复核时再保留 `review.md`；
  已失效的 `spec.md` 和 `plan.md` 由 Git 历史保存，不在当前树无限累计；
- 案例只保留能解释长期规则来源且无法由规则本身说明的代表性事件，不要求一项规则一个案例；
- 轻量工作直接更新当前事实或留下简洁结果，不创建四文件目录。

## 新会话启动

新会话按仓库启动顺序恢复事实后：

1. 从 `docs/status.md` 读取唯一活动工作；
2. Codex 以项目规划者身份与用户讨论下一步，复杂或模糊时使用 Plan 模式；
3. 不继承旧会话的 CLI 额度、授权、Worker 选择或尚未派发的开发方向；
4. 双方形成开发决定后，Codex 生成新的 CLI 状态卡；
5. 用户选择 Worker；
6. Codex 创建隔离工作树并发送自然委托，随后向用户逐字公开消息；
7. Worker 自己维护过程文档、实现和验证；
8. Codex 对 Worker 的每次回复向用户提供关键摘要。

如果用户尚未决定首个任务，新会话停在讨论阶段，不为了测试流程而制造任务。

## 规则演化

本规则从 `2026-07-24` 起直接生效，不再设置前置实验门。实际使用出现覆盖、上下文漂移、
额度读取失败、协调成本过高、重复推理或产品推进变慢时，先修复具体问题，再按证据修改本
文件。不要提前建设自动调度层；只有重复摩擦证明手工流程不足时才考虑代码化。
