# 元开发

> 本文件是本仓库对“元开发”的唯一权威定义。`AGENTS.md`只保存摘要和路由，当前有效规则分别落在 `AGENTS.md`、`docs/meta/` 与 `docs/engineering/`。

## 定义

**元开发（Meta-development）是以“Agent 如何开发产品”为直接对象的开发活动。**
它不以新增产品功能为直接目标，而是改进 Agent 从需求理解、上下文恢复、规格拆解、
执行协作、验证复核到规则演化的工作系统，使产品开发更高效、可接管、可验证，并保持
结论真实。

判断一项工作是否属于元开发，要看它的主要改变对象，而不是文件类型或是否编写代码：

- 改变“产品向用户提供什么”，主要属于产品开发；
- 改变“Agent 怎样更可靠地开发产品”，主要属于元开发；
- 同时改变两者时，必须声明主要目标，并分别验证产品结果与治理效果。

元开发可以产生规则、文档、检查脚本、CI 门或开发工具；只要它们的直接目标是改进开发
系统，而不是向产品用户提供新行为，就仍属于元开发。

## 范围

元开发包括五类工作：

1. **规格驱动开发**：把需求转化为边界清楚、可验证、允许结论明确的增量；
2. **上下文工程**：组织权威事实、当前状态和历史边界，使接手 Agent 能从文件恢复现场；
3. **AgentOps**：管理 Agent 路由、单写入者、风险分级、授权、预算、检查点和恢复；
4. **验证治理**：选择测试层级、独立复核、允许结论、失败分类和停止条件；
5. **规则演化**：从真实开发摩擦形成假设，经产品增量验证后保留、修订或撤回规则。

## 不属于元开发

- 普通产品功能实现、常规缺陷修复或仅改善运行时代码结构；
- 单纯整理文档、移动目录或增加流程、测试、审计和 Agent 数量；
- 没有影响产品推进、结论真实性或可接管性的个人偏好；
- 未经用户决定或证据支持，却由 Agent 自行泛化成长期规则的一次性经验。

这些工作可能为元开发提供观察材料，但本身不会因此自动成为元开发成果。

## 进入与退出边界

- 一次性不便先作为观察，不直接升级成规则。只有反复出现的摩擦，或一次已经实质威胁
  产品结果、授权、费用、隐私、结论真实性或可恢复性的系统性失败，才允许提出元开发变化。
- 元开发成为活动增量前，必须说明受影响的产品结果或关键未知、最便宜的证伪方法、最小
  治理变化、投入与停止线、产品验证载体和允许形成的结论。
- 默认先用真实产品增量验证准备保留的治理变化；“产品仍能完成”不自动证明规则有效，
  还要判断原摩擦是否减少，以及治理成本是否与收益相称。用户可以明确决定直接采用一项
  可逆规则；此时必须记录采用边界，并在实际问题出现后按证据修订，不能虚构验证结论。
- 元开发增量必须事先定义完成条件，完成后立即返回产品主线；治理重构没有天然终点，
  不得以“彻底”为名无限扩张。

## 验证与裁决循环

```text
真实摩擦/失败
→ 原因假设
→ 最小治理变化
→ 用于验证的产品增量
→ 实际效果
→ 保留 / 修订 / 撤回
```

裁决或用户明确采用后：

- 保留的规则写入 `AGENTS.md` 或相应 `docs/engineering/` 文件；
- 修订或撤回的规则必须同步清除旧表述，并记录不能继续成立的结论；
- `docs/meta/evolution-log.md`保存治理变化索引；
- `case-studies/`只保存无法由当前规则本身说明的代表性案例，案例叙事本身不提供当前授权；
- 标准或完整元开发增量仍在 `docs/work/active/<slug>/`执行；完成后把规则、必要案例和
  演化索引提炼到当前权威文件，并删除重复的活动 / 完成工作包；
- 不为一次实验建立永久目录；规范化输入、停止线和结果先写入唯一活动工作，保留的结论
  直接进入当前规则，未保留的过程由 Git 历史恢复。

不要把原始聊天、stdout、wire dump、凭据、Provider 原文或历史证据树当作“学习”保存。
应保存足以解释问题、决定、验证、实际效果和限制的规范化证据。

## 文档保留

- 元开发：规则优先；演化日志只做索引；案例必须有代表性；完成工作包在提炼后删除。
- 产品开发：完成目录只保留规范化 `result.md`，存在强制独立复核时再保留 `review.md`。
- `spec.md` 与 `plan.md`只服务活动执行，完成后由 Git 历史保存，不在当前树长期累计。
- 相同事实只保留一个权威正文，其他入口使用短链接，不复制全文。
