# 设计说明

## 为什么采用受控 Workflow

本产品解决的并不只是“生成流畅文本”。客服草稿可能遗漏停止条件、混淆产品型号、虚构已完成动作，或让可执行主张失去来源。设计因此把 LLM 生成限制在确定性的控制面之内。

## 核心流程

1. 在 transport 构造前检查敏感范围、声明的安全事件和明确的型号独占能力冲突。
2. 按已知产品型号过滤并检索有上限的证据集。
3. 要求模型用自然语言枚举义务、选择支撑 clause，并对所有 clause 作完整互斥分区；
   宿主由此机械派生来源和忽略上下文。
4. 依据义务清单生成客户可见回答或工单草稿。
5. 由模型声明来源主张与客户可见片段的语义对应；宿主机械校验片段存在、来源绑定、
   来源跨度位于该义务所选 clause、义务覆盖和禁止出现的完成态主张。
6. 返回可审核候选或类型明确的转人工结果；最终由人工决定。

## 关键取舍

- 检索质量由离线评测证明；运行时不宣称知道召回率的完整分母。
- 与其输出无证据支持的可执行陈述，不如转人工。
- 结构化元数据不能替代客户可见正文中缺失的事实。
- LLM 负责义务与 clause、来源主张与客户表达之间的开放域语义对应，宿主不以逐字相等
  冒充语义判断；宿主只验证可观察的身份、分区、跨度、来源、集合和硬门。
- 模型没有工具、数据库访问、重试权限或业务动作权限。
- 预算、隐私与声明的业务边界检查发生在构造传输层之前。
- 确定性边界只覆盖公开合成知识已经明确的规则，不声称解决开放域语义安全。

## 可重复的检索体检

`evals/retrieval-checkup-v1.json` 冻结了 16 个公开合成问题，R1 / R2 各 8 个，覆盖六份
资料的 27 个有效章节；11 个问题要求同时找回多个章节，10 个包含口语、长描述或自然改写。
`tools/retrieval_checkup.py` 在型号过滤后，用同一题集分别运行现有 BM25、本地 BGE 和
BM25+BGE+RRF。第一次冻结结果由 `web/app/lib/retrieval-checkup-v1.json` 保存并直接供
公开设计页渲染：

| 检索方式 | Top-5 全部必需来源 | Top-10 全部必需来源 | Top-10 错误型号来源 |
| --- | ---: | ---: | ---: |
| BM25 | 14 / 16 | 16 / 16 | 0 |
| BGE | 14 / 16 | 16 / 16 | 0 |
| BM25+BGE+RRF | 16 / 16 | 16 / 16 | 0 |

这里的“全部”是逐题检查所有预先标注的必需章节，不是单个来源命中率。该开发集可以说明
混合排序在这 16 题上补回了两种单路检索的 Top-5 遗漏，但不能外推为线上成功率、回答
正确率或开放域能力。它没有使用未见 HOLDOUT，也没有调用 Provider。冻结运行后本切片
停止，不根据输赢换题、调参或改变产品 Top-10 行为。

## 回放语义

回放数据是经过标注和验证的产品结果，用于在实时体验关闭或不可用时保持作品集可用。它不会被展示为一次新的模型调用，也不能据此形成发布级质量主张。
