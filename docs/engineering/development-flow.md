# 开发流程

> 协议：`light-governance/3.0`
> 生效日期：`2026-07-31`

## 默认立项

实施前默认只需回答开工三问：

1. 这次做什么？
2. 这次不做什么？
3. 怎样算完成？

三问可以记录在 Conversation、PR 或必要的活动工作文件中，不默认创建 Task / Run 或完整
规格。任一答案不清楚就不得进入实现。治理、测试或文档数量不能代替产品进展，轻量立项也
不能降低测试、运行证据、回滚、可观测性或事实回写要求。

## 复用审查

依次检查：

1. 仓库中已经验证的行为或 fixture。
2. 已采用的依赖。
3. 仍在维护且许可证兼容的开源库。
4. 厂商官方 SDK/API。
5. 项目专用的薄适配层。
6. 只有当前述选项确实不满足语义、许可证、安全、兼容性、成本或维护要求时，才建设新的通用基础设施。

## 工作规模

- 轻量：一个局部、可逆边界，不涉及公共合同、持久化、安全或外部风险。
- 标准：跨多个文件的用户可见行为，或一个有界接口。
- 完整：架构、API 合同、持久化、安全、隐私、公开发布、破坏性迁移或 Provider 机制。

多个 Task 可以在隔离工作树中异步并行。需要隔离、候选或恢复治理时，标准 / 完整产品结果
可以使用规范化工作目录；一个目录可以承载多个相关 Task，一个 Task 也可以通过多个 Run
接续。中间修复保留在对应结果目录或候选中，不重复制造治理循环。同一可写工作树仍只有
一个写入 Run。

只有“完整”工作，或任何触及部署、费用、安全边界、`R2` 的工作，必须形成完整 Task 规格，
并在三问之外记录：

1. 用户将新增得到什么，或消除哪个关键未知；
2. 最便宜且最可能证伪该方向的检查；
3. 可以复用的仓库能力、依赖、开源方案或厂商能力；
4. 最大投入和停止条件；
5. 检查通过后允许得出的结论。

未来候选、活动事实、PR 和完成回执的所有权转移见
[`github-lifecycle.md`](github-lifecycle.md)。机器检查、当次授权与条件式评审兜底见
[`review.md`](review.md)。

## 外部风险与成熟度

风险：

- `R0`：无网络、费用或外部写入。
- `R1`：仅合成/公开数据，固定 Provider，调用和费用可封顶，无业务写入。
- `R2`：涉及敏感数据、账号/公开状态、外部写入、不可逆操作或无法封顶的费用。

成熟度：

- `S0 exploration`：最便宜的公开/合成实验；不使用私有 HOLDOUT，也不建立正式保管系统。
- `S1 development`：覆盖代表性公开切片和压力切片；没有未解释的结构失败。
- `S2 candidate`：干净的固定提交、集成测试和适用的机器门 / 授权。
- `S3 formal`：固定候选、新的正式输入、授权、预算和严格结论合同。

阶段标签不授予网络或费用权限。候选质量失败时仍应完成有效证据收集；授权、传输、预算、身份或包完整性失败时必须停止执行。

## 验证说明卡

任何可能改变模型质量、产品就绪度、候选成熟度或发布主张的验证，都必须预先声明：问题、非目标、样本、代码/prompt/模型身份、重复次数、评分方式、硬门与质量门、泄漏控制、最大调用/费用、停止条件和允许结论。

只有完全满足 `AGENTS.md` 中的全部条件时，常设授权才适用。Stage 12 不属于常设授权范围，必须使用独立说明卡并取得明确批准。

## 停止规则

- 先运行最便宜的证伪检查。
- 连续两个循环仍未改善用户路径、已声明指标或关键未知时，停止该方向。
- 如果治理/评测基础设施开始大于产品改动，必须证明它此刻确有必要，否则延后。
- 已揭示 HOLDOUT 和失败候选只能作为回归输入；不能据此形成新的正式结论。

## 完成条件

只有当用户可观察行为或关键未知确实发生变化、相关机器检查通过、所需当次授权已记录、
触发的方案级评审疑问已关闭、当前事实一致、限制明确且形成有界提交时，一个产品结果才算
工程完成。Run 结束、Task 候选、Delivery 应用、部署和用户验收是彼此独立的状态。
