# 三层拦截与评审兜底

> 原则：轻的是事前审批，不是事后证据。默认用机器检查和明确授权拦截风险，不把独立评审
> 当成每个候选的仪式性关卡。

## 机器层

机器能够稳定判断的事实必须进入 CI，并在变化时失败关闭：

- `governance` 使用 `check_public_repo` 检查公开仓库安全、固定资产、回放合同、部署结构和
  已登记的关键状态词存在性；
- Web、API 和容器 Checks 验证各自登记的产品合同，`ci_proof` 明示每条主张、证明边界与
  跳过状态；跳过或未执行不构成证明；
- 运行时变更合入 `main` 后，部署链继续用不可变 manifest、健康检查、公开路由和回滚回执
  核对实际部署。

现有绿色 Checks 只证明已经登记且实际执行的断言，不等于所有公开文字都已核实。README、
公开页面或其他公开文档新增或改变机器可判定的主张时，相关产品变更必须同时：

1. 在 `docs/product/evidence-map.md` 绑定代码、测试、部署或运行证据；
2. 把可判定事实写入 `check_public_repo`、产品测试或部署 Workflow；
3. 从独立事实源读取实际状态，而不是在测试中重复目标文案；
4. 让主张与证据漂移时对应 Check 失败。

缺少可执行覆盖时，不得用 CI 绿灯宣称该主张已经自动核对。单纯检查关键词出现、人工读过
文档或在 PR 描述中列出证据都不能替代机器断言。

## 授权层

以下变化必须取得用户对本次具体动作的明确确认：

- 费用或新的 Provider 调用；
- 公开、生产或其他外部写入；
- 安全边界；
- 公开主张。

这是授权，不叫复核。确认必须绑定本次候选、动作和已说明的外部影响；Conversation、Task、
Issue、Git 文件、历史授权或 Reviewer 意见都不能授予权限。已有自动部署常设机制只授权
固定执行路径，不授权某个候选：运行时 PR 的合并会触发生产写入时，用户必须先当次确认精确
候选及生产后果，随后流水线自动执行而不增加人工 Reviewer。自动化不能自行扩大费用、写入
目标、安全边界或公开主张。

## 评审兜底

只有同时满足以下条件时才派独立只读 Reviewer：

1. 关键问题无法由现有或本次可合理补充的机器断言验证；
2. 存在会影响方案选择的真实疑问，而不是实现者已经能够用代码、测试或运行结果回答的常规
   工程问题。

方案级疑问是不同可行方案可能改变用户行为、授权、费用或结论真实性。库、文件、类、测试
形态、措辞偏好和无行为影响的风格争议不触发评审。

Reviewer 只读明确的问题、选项、证据和必要 diff，不修改工作树、不提交、不推送，也不
代替实现者修复。若疑问针对固定候选，记录 `candidate_sha`；若疑问发生在实现前，固定问题、
选项、证据和允许形成的结论即可，不必等待绿色 Draft PR 后再制造一次全量审计。

## 发现与关闭

评审输出至少包含：

- 需要裁决的方案疑问和机器不能验证的原因；
- 读取的证据与适用边界；
- findings 及其对用户行为、授权、费用或真实性的具体影响；
- 明确结论和仍未知的部分。

只有确实会改变用户行为、授权、费用或真实性的 finding 可以阻断。其余意见一律降级为
建议，不得延迟合并；用模糊风险、个人偏好、重复机器已证明的事项或与批准入口无关的边角
问题制造阻断，视为评审失职。

实现者关闭有效 finding 后，先运行相应机器检查；只复查原疑问及覆盖 diff，不重复审计
未变化区域。候选变化会使绑定旧 SHA 的结论失效，但不会自动触发全量评审。
