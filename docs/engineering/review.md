# 独立复核

## 正式复核门

只有以下变化强制正式独立复核：

- 元规则；
- S2 / S3 成熟度或正式结论；
- 生产、发布、回滚或部署授权；
- 安全、隐私、认证、费用或持久化；
- 公共 API / 合同或公开主张。

普通 R0/R1 UI、文案和缺陷修复不强制独立复核，由自动化、负责当前候选的写入会话 Agent
和适合的产品验证关闭。
若它们同时触及上述边界，按触及的高影响门处理。

## 调用时机

1. 负责当前候选的写入会话 Agent 完成实现和本地相关检查。
2. 提交并推送 Draft PR。
3. 等待 `governance`、`web`、`api`、`containers` 全部成功。
4. 记录 Draft PR head SHA，停止对该候选写入。
5. 调用一个只读复核者，对固定 SHA 做一次完整复核。

实现期间的咨询、日志分析和测试探索不是正式复核，不能产生批准回执。复核者不得修改工作
树、提交、推送或代替当前写入会话 Agent修复。

## 回执

正式回执至少包含：

- `candidate_sha`
- 复核范围与风险
- 已通过的 Checks
- findings（严重度、可批准入口、威胁模型）
- 结论边界

只有同时满足“从批准入口可达、位于已声明威胁模型、会改变用户行为 / 授权 / 费用 / 隐私 /
结论真实性”的 finding 才阻断。

## 候选变化

候选变化立即使旧回执失效，但不自动触发第二次全量复核：

- 没有 finding：不修改候选，不增加复核轮次。
- 有 finding：当前写入会话 Agent 修复、提交并等待 Checks 再次全绿；只复核原 finding 和
  覆盖 diff。
- 覆盖 diff 引入新的高影响边界：扩大相应范围，但不重复未变化区域。

每个 worktree 始终只有一个写入者。复核成本、轮次、有效 findings 和候选失效必须记入活动
结果，以便在收口时判断该门是否值得保留。
